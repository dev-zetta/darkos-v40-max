# Audio follow-up, 2026-11-15

This is the historical V4 trial record. The later [battery/status investigation](BATTERY_STATUS_20261116.md) replaces the frontend and adds focused mainline gauge/DC reporting changes while retaining the unresolved audio findings below.

Linux 7.3.4-v40.1 remains installed. Frontend V4 SHA-256 39339a1e77bcc7582958a807751a62de2e79bcac91a0918a0094c79c1feb48ac and its matching integrity consumers were installed and verified; the user reported menu sound unchanged or worse. Menu background music is now disabled by user preference, while debug logging and game sound remain enabled. The default source recipe continues to select V3. No new kernel or codec change was installed during this follow-up.

The experimental perfmax helper was tried with the existing CPU/GPU operating points. Two PSP launches froze the device, including network access. Restoring the prior helper SHA-256 22820af9c8dd39095db25484d7adb566b017865795f682c64b89b90bbf7d6f27 restored successful game launch. The successful comparison also reached GPU 480 MHz using simple_ondemand; the failed candidate used userspace. The policy/transition path remains a hypothesis, and neither a frequency-only cause nor a precise kernel fault has been established. Retain the rollback and exclude that candidate from routine deployment.

In Alien Syndrome, PPSSPP's running overlay showed approximately 58–68 percent emulation speed, about 460 frames queued against a 3360-frame target, and increasing emulator underruns. ALSA's kernel xrun counter stayed zero, which does not exclude shortages padded by PPSSPP's classic resampler. With frame skipping and sound settings unchanged, the user selected 1x PSP rendering instead of Auto and reported near 100 percent speed and cleaner music. Normal exit saved InternalResolution=1 in both ppsspp.ini and ppsspp.ini.sdl; diagnostic display flags were also turned off through the UI. This is acceptance for the tested scene, not every game or complete elimination of noise. Three existing per-game profiles retain their previous 2x rendering and frame-skip overrides; these can supersede the new global choice. The additive PSP configuration helper does not silently replace those preferences.

The remaining idle noise is a separate user-reported static/buzz with occasional cracks, present with menu music off and changing slightly with button presses. Five snapshots of the exact 16 KiB ALSA playback ring were all zeros. The read-only capture duplicated the verified frontend's existing PCM descriptor with pidfd_getfd and mapped only its playback ring; a prior /proc/pid/mem attempt was refused with EIO and supplied no samples. Minimum DAC Playback level left the noise unchanged. Closing the frontend's PCM made the noise much quieter and stopped the cracks according to the user; they returned when the menu reopened. ALSA reported closed and codec DAPM reported DAC L/R, headphone stages, charge pump, clocks and bias supplies off during the closed interval. The menu and original hardware level were restored. The installed volume callback's inherited floor/floor scaling required correcting one readback step on restoration; no volume patch was installed. These observations implicate the active output path but do not identify an individual faulty component or register.

Upstream has related historical reports. [ArkOS4Clone issue 462](https://github.com/lcdyk0517/arkos4clone/issues/462) describes static and scrolling-related noise; [issue 463](https://github.com/lcdyk0517/arkos4clone/issues/463) describes hiss. Users and the maintainer report recovery after disconnecting the battery, alongside a battery-driver correction. The [September 3 battery commit aa40d04](https://github.com/lcdyk0517/arkos.bsp.4.4/commit/aa40d04fe4eb96b68e77518b81c58ee4c35b66ad) removes learned-voltage storage from PMIC addresses 0xc6–0xc9 and stores it in /var/lib instead. The current upstream mainline RK817 charger/fuel-gauge source does not contain that old hybrid-storage scheme. A read-only inspection of those four addresses did not yield valid learned-voltage anchors; this does not establish either PMIC corruption or a need to rewrite reserved registers. No battery disconnect or PMIC reset was performed in this investigation.

All six direct BSP forks' codec and battery file histories were inspected, alongside the active 5.10 kernel fork and targeted distribution reports. [GreekAdonis commit 9e1e322](https://github.com/GreekAdonis/arkos.bsp.4.4/commit/9e1e3221515457ddb46570a54f294e131b074bfe) adds DAC mute and optional amplifier-GPIO gating at volume zero; [ba1402a](https://github.com/GreekAdonis/arkos.bsp.4.4/commit/ba1402a1d3af2a518e94fe4c2d62a9feb36699ff) extends this to the effective volume floor. This is relevant to idle-output noise, but it is a 4.4 vendor-driver implementation with GPIO assumptions absent from the captured working board tree. It was not applied to mainline or accepted on this hardware. [Issue 368](https://github.com/lcdyk0517/arkos4clone/issues/368) also distinguishes low-volume leakage from residual crackling.

The upstream codec change [50730f0](https://github.com/lcdyk0517/arkos.bsp.4.4/commit/50730f03beb8d05d6c928e2cd7dabaf0571f722e) proposed rate handling, stream-restart and amplifier-idle corrections, but was [reverted by e555805](https://github.com/lcdyk0517/arkos.bsp.4.4/commit/e555805f8e99601309746310185991e44c62c1d3). Its title is not evidence of a validated repair to import. Current captured 44.1 kHz common-rate PLL and headphone-pump/stage settings match the applicable retained vendor values. The checked recent upstream OS commits/PRs contain no verified repair for this exact mainline idle-noise case. Board-specific output muting/power sequencing remains the next investigation; no unverified amplifier GPIO or reserved PMIC write is justified by these reports.

# Idle static and crackling investigation, 2026-11-16

The user still hears idle static/crackling with menu music disabled after the focused battery/DC fixes and frontend V6. Five new read-only samples of the active 16384-byte PCM ring were entirely zero, repeating the earlier observation on the new kernel. The confirmed battery-percentage and charging-display repairs therefore did not eliminate this independent noise. This does not establish whether a power rail, DAC output, external amplifier or electrical coupling is responsible.

## Controlled live comparisons

The first comparison asserted only the documented DACMT bit at codec register 0x38 bit0 for a nominal forty seconds. A temporary exact-board helper used the bound parent's serialized regmap API, queued automatic recovery before its mutating work, and restored on timeout and removal. Exact kernel vermagic and all 29 imported symbol CRCs matched; 59 actual-source lifecycle/guard/I-O/restoration cases passed with UBSan. The running test verified digital mute held on, with analog power, clocks, gain, the DAPM graph and frontend process unchanged. The user reported noise unchanged. Original register values and graph were restored, and the helper was unloaded.

The second comparison used normal ASoC DAPM pin APIs to disconnect the codec HPOL/HPOR/SPKO outputs and the card Speaker/Headphones endpoints temporarily. All five original connected/force states were saved and restored, including the originally disconnected Headphones sink. The helper passed all 30 imported CRC checks and 321 actual-source lifecycle/pin-state/error cases with UBSan. During the nominal forty-second live interval, physical register readbacks and widget state confirmed DACs, headphone stages, charge pump, codec PLL/clocks, bias and codec LDO off. The existing frontend process and PCM stream remained running; frontend CPU time advanced by approximately 18.9 CPU-seconds over 41.5 wall seconds. The user reported noise unchanged. Original pins, power mask, sampled registers and DAPM graph were restored, and the helper was unloaded. This removes the earlier whole-service-stop ambiguity without identifying the remaining noise source.

The third comparison paused only the frontend's threads for forty seconds, with an independent identity-checked automatic-resume timer. PCM and sampled audio registers remained unchanged and running; process CPU time stayed fixed while stopped. The user reported more cracks. The same process resumed, all sampled audio state matched its preimage and the recovery timer was removed. Thus simply reducing frontend execution did not cure the noise; this does not separate CPU-idle power behavior, bus activity or electrical coupling.

The user independently reported static at volume zero; that is a user observation, not a simultaneous verified hardware-gain capture. The controlled comparisons held the captured DAC gain registers at 0x12/0x12, the board mapping's maximum, without changing gain. No persistent setting or kernel image changed, and temporary helpers are diagnostic artifacts outside the default source recipe. Noise persisting with codec output stages off weakens a DAC-only explanation; external amplification, shared supplies, I2S/USB activity and coupling remain candidates.

## USB adapter contribution

The user physically unplugged the AX900 adapter for approximately one minute: the cracks stopped, but static with occasional frequency changes remained. Reinsertion and Wi-Fi reconnection returned the repeating cracks. A detached read-only local logger preserved the same frontend identity, PCM ownership and codec register values. Descriptive stable intervals before/during/after the load reduction showed median battery currents of approximately -631/-440/-629 mA and voltages 3.541/3.578/3.534 V; frontend CPU rates were similar. This is not a precision adapter-current measurement or a matched-duration benchmark.

USB sysfs entries remained present through most of the physical comparison. Kernel logs instead showed USB-control timeouts, hardware-rfkill disable and deauthentication before delayed hub cleanup and re-enumeration. The short interval without a sysfs object is therefore not the physical unplug duration. The hub driver's generic EMI-question wording does not prove RF interference. Removing the composite WLAN/Bluetooth adapter changes radio activity, USB traffic/interrupts, current draw and coupling together.

Standard WLAN power saving was on, while USB power/control was already on and runtime-active throughout the captured connected intervals. A separate fifty-second iw power-save-off comparison retained the connection and unchanged sampled audio state; the user reported cracks unchanged. Power saving was restored on, verified, and its independent recovery timer removed. No power-save policy or module parameter was installed as a fix.

A detached seventy-second WLAN-only soft-rfkill comparison then kept the composite adapter physically attached. Exact interface/phy/USB identity checks selected only its WLAN entry; sixty-five samples verified soft-blocked/hard-unblocked state across approximately seventy seconds. The frontend and onboard PCM owner stayed unchanged, and sampled codec registers, DAPM state and the other Bluetooth rfkill entry matched their baselines. The user reported no improvement. Normal WLAN state and the existing saved connection were restored and verified, including the independent recovery path; temporary units and RAM staging were cleaned up.

Software radio blocking is not equivalent to physical USB removal. The source audit identifies hardware-rfkill polling that can continue while WLAN is stopped; the comparison did not trace individual USB requests or establish their cadence or acoustic correlation. It therefore does not exclude adapter power/current draw, remaining USB traffic, Bluetooth activity or electrical coupling as contributors, nor identify any of them as the cause.

## USB-C digital-output reference

The USB-C earbuds enumerated as a separate UC02 USB Audio playback device alongside the onboard codec, with both earbuds and WLAN adapter attached through a USB hub. A bounded forty-eight-second reference explicitly opened the USB PCM at 48 kHz, signed 16-bit stereo and played quiet faded 440/880 Hz beeps separated by digital-silence gaps. The onboard frontend and its existing PCM continued running. All forty-eight USB samples reported no xrun, playback exited successfully without stderr, and the USB PCM was closed before and after the reference. No default output, mixer or frontend setting changed.

The user recognized the beeps but still heard static/cracks, including before playback while the USB PCM was closed. This establishes functional USB playback and shows that the reported noise did not require an active USB playback stream; it does not prove the transmitted samples were corrupted or locate the electrical noise source. The USB device remained powered when its PCM was closed, the onboard PCM remained active, and the hub/output change also changed the USB power and traffic topology. This was a qualitative listening comparison, not a calibrated or level-matched noise-floor measurement.

## Bluetooth reference

The Fresh 'n Rebel 3ATW4000 earbuds paired successfully. A private BlueALSA 4.3.1-3 daemon and ALSA plugin were extracted from Debian packages verified against signed repository metadata and run from RAM with a private D-Bus name; no system audio package or default PCM was replaced. A2DP used SBC, stereo and 48 kHz. The onboard frontend and its existing PCM stream continued unchanged. A first stream was inaudible, and two subsequent levels were too quiet for a useful noise comparison. These attempts are not clean-audio acceptance.

The final 48-second reference used faded 440/880 Hz beeps with silent gaps, peak 9216/32768, and the private software volume at 70 percent. PCM properties confirmed Running=true, SoftVolume=true and raw stereo volume 0x5858. At this useful listening level the user reported clean gaps. This is physical acceptance of that reference over Bluetooth, not all game audio or every Bluetooth workload. It was performed on the later charging boot with the direct composite dongle; the USB-C comparison used a hub during the preceding boot, so it is not a matched simultaneous A/B measurement.

Clean Bluetooth alongside reported noise on the onboard output and powered USB-C earbuds strengthens a shared power/electrical-path hypothesis. It does not localize the battery, PMIC, USB supply, grounding or an amplifier, and does not exclude every software or transport defect. The Bluetooth earbuds have their own power and analog stages. A low-level synthetic reference is not a test of emulator underruns under full load.

Playback ended successfully, the private observable volume was restored, and all test streams closed. The temporary daemon, D-Bus policy, controller power and native Bluetooth service were restored to their inactive baseline; the UPower instance activated by this test was stopped without changing its enablement or thresholds. Recovery timer and inhibitor were stopped, transport logs were preserved and private RAM files were removed. The user-requested pairing bond remains. No new kernel image, gain mapping or permanent audio route was installed.

After restoration the user confirmed that both the original speaker static and repeating cracks were still present. A fresh same-boot read-only capture retained the HP route, 44.1 kHz stereo S16 PCM, enabled 11.2896 MHz I2S1/MCLK and no new reported audio I2C error. Successful Bluetooth playback therefore did not repair the speaker output.

## Original configuration and physical-board uncertainty

The shipped 2021 kernel, later working 2026 BSP image and current mainline build are separate baselines. The exact source/configuration of the two old binaries has not been reconstructed. Both shipped and later working device trees identify RK817 and I2S1 at 0xff070000, with the same I2S pins, CPU-master/codec-slave format, 256-times MCLK ratio and headphone-detect input. The current 44.1 kHz stream and revision-5 PLL values agree with that retained configuration. This establishes the correct codec family and consistency for the captured stream; it does not establish every rate or transition.

The old output states are also distinct: a saved November 10 mixer says SPK, while running November 13/14 BSP captures say SPK_HP. Neither is a direct shipped-factory live mixer capture. Mainline HP restored physically confirmed speaker music, while the mainline SPK route was silent. The original device tree declares HPOL/HPOR headphone routing without an amplifier component or verified amplifier-control GPIO. Mainline also declares a Speaker/SPKO endpoint, but its current HP mux powers the headphone DAC/stages with Class-D off. A widget named Speaker being On is not proof that the internal Class-D stage drives the physical speaker.

No schematic or traced connection yet distinguishes a directly driven speaker from an external amplifier or establishes a usable enable pin. The retained BSP's additional analog startup/PLL timing also differs from generic mainline DAPM sequencing. Consequently the correct codec and working HP route do not prove complete analog-configuration equivalence or a clean output. A different clone's amplifier GPIO must not be substituted for this missing board evidence.

A model-labeled motherboard image is indexed on the [V40 MAX wiki page](https://handhelds.wiki/V40_MAX), but full-resolution access returned HTTP 403 during this check and its PCB revision/component markings were not verified. The [owner's R36Plus teardown](https://retrohandhelds.gg/r36plus-review/) documents a built-in-Wi-Fi V20 board and other boards sold under similar names; that unit is not established as this handheld's PCB. Useful next evidence is a photograph of this unit's PCB/revision plus readable component markings near the speaker, headphone jack and USB/DC connectors. No disassembly or board-level electrical change was performed by this software investigation.

## Battery register interaction

The historic [ArkOS issue 462](https://github.com/lcdyk0517/arkos4clone/issues/462), [issue 463](https://github.com/lcdyk0517/arkos4clone/issues/463) and [vendor correction aa40d04](https://github.com/lcdyk0517/arkos.bsp.4.4/commit/aa40d04fe4eb96b68e77518b81c58ee4c35b66ad) remain relevant leads. Reports of recovery after battery disconnection do not explain the internal reset mechanism or prove the current noise has the same cause. Mainline does not contain those old battery-anchor writes to 0xc6..0xc9.

The previous blanket description of those addresses as reserved was too broad. Rockchip's [RK817 Datasheet Rev2.1](https://atta.szlcsc.com/upload/public/pdf/source/20240126/1D84E9BEA212072F9DD3BF1F36FC3510.pdf), pages 113–114, documents 0xc6 as a mixed-purpose register containing power controls and I2S_RX_MST bit4. Current readback is 0xc6=0x64 and codec clock mode 0x48=0x00: both select codec slave, consistent with the intended CPU-master setup. Register 0x49 is a divisor, not that master/slave control. This excludes a currently asserted RX-master bit at 0xc6, not every retained PMIC state or signal-integrity fault. The datasheet does not establish that codec-local reset clears undocumented 0xc7..0xc9; no whole-byte PMIC reset or unknown-register write was attempted.

## Driver audit

The exact compiled codec remains SHA-256 99d1f97f8c8bedf00123056322bf98a2f1f33685853f08f69db22d1eab8ca573, unchanged by the battery/DC update. New DC support reads an input and updates reporting; gauge bookkeeping addresses do not overlap the codec's audio registers. Current buck-regulator modes match the factory NORMAL selection. No amplifier-enable GPIO is established by the retained working runtime device tree. The accepted HP-DAC speaker route remains selected.

Fresh mainline and official Rockchip histories identify real vendor clock/bias sequencing work, including [19e4b7da3917](https://github.com/rockchip-linux/kernel/commit/19e4b7da3917191c274947a3c351fb8419c86a93). Eleven relevant authored vendor patches failed direct zero-fuzz applicability to the current mainline architecture. Mainline already enables MCLK before codec reset, and the board's volume mapping already avoids vendor-disallowed DAC values. The timed bias/clock sequencing difference remains a source-port hypothesis, not a demonstrated repair for continuous static. Any experiment must preserve current routing and distinguish transition pops from powered idle noise.

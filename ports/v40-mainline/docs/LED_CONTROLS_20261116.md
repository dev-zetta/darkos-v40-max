# V40 LED identification, 2026-11-16

The actual unit has a small status light between SELECT and START and separate static multicolor thumbstick rings. GPIO2_B5 is physically confirmed to change the center status light between colors; it did not change either ring. Center-light off is not physically confirmed. No thumbstick on/off pin is established at this checkpoint, and no broad GPIO output sweep is justified by an unclaimed line alone.

The original bootloader was inspected directly from the preserved stock card image, not inferred from the original kernel's build date. Its version is U-Boot2017.09-g120aff9560-dirty, built July19,2025; payload SHA2562cabcff6a34b7f5595a24fbb4395e7489a9565dc724e815b0caa9a978b63366b. The literal13/18 labels and GPIO call sequences were checked in the retained binary. The dirty version suffix does not establish an exact source rebuild.

The GPIO2_B5 comparison used only the normal Linux GPIOv2 character-device API for changes. Read-only mappings captured the target mux, direction, latch, pull, drive and Schmitt fields before/during/after; no raw-register write was used. The independently reviewed helper passed fourteen host ABI/lifecycle fixtures, including compiled Linux GPIO header layout checks. A twenty-second lead-in preceded ten seconds each of output-high, output-low, input with original pull-down and input with bias disabled. All forty samples passed target readback. Original input/latch0/pull-down/mux0 returned before the fd closed; the independent recovery timer also confirmed restoration. Host fixtures do not substitute for physical LED observation.

GPIO numbers are not portable between the old BSP and mainline. In the tested mainline boot, chip bases were512/544/576/608: legacy linear77 corresponds to bank2 offset13 and sysfs number589. Helpers must identify the chip by label, physical controller and offset rather than export literal77. Closing a GPIO character-device fd does not restore hardware direction, output latch or mux; these require explicit normal-API restoration and readback. GPIO requests must also refuse other owners and changed mux state.

The original stock userland and enabled startup service are direct status-light evidence. Its charger child also contains bat_low_gpio, but the nearest retained BSP battery helper reads its own node, so the property and helper alone do not prove that exact old binary executed that branch. Preserve that distinction when porting the LED model.

[Upstream console-detect](https://github.com/lcdyk0517/console-detect) marks the r36splus profile's joystick LED backend unsupported. The frontend contains GPIO, dual/single-GPIO, MCU, WS2812 and R36Ultra backends for other boards. Their existence is not this PCB's wiring evidence. In particular the MCU backend's hardcoded legacyGPIO65 overlaps this unit's volume-down input, while its UART transport uses the serial-console path. Those controls must not be applied merely because the rings are multicolor. Static multicolor rings do not distinguish a software-controlled controller from fixed powered LEDs.

The audio investigation remains independent: neither a physically unverified heartbeat-off interval nor status color control is a demonstrated repair for static/cracks. The unexecuted backlight and process-only dummy/null-audio comparisons remain candidates outside the default installation. No permanent LED driver, DTB, kernel, GPIO policy or user setting is installed by this identification checkpoint.

The GPIO0_B5 repeat uses ordinary GPIO transitions at a nominal half-second per level (one full cycle per second); it does not configure hardware PWM. The exact PX30 pinmux groups do not define PWM on that pin. PWM2 is instead GPIO2_B5, already identified as the center-status candidate, and PWM3 is the legacy GPIO0_C1 heartbeat. Their existence does not identify ring control. Original output-low, pull-up, mux and other sampled pin fields restore before line release; fixture, electrical readback and visible-ring acceptance remain separate evidence levels.

GPIO0_C2 was tested separately only after an exclusive idle-adapter check and completed normal unbind of I2C1 at ff190000.i2c; the PMIC remains on separate I2C0. The shipped DT already enables this same 400 kHz I2C1 bus and selects C2/C3, so its ownership is not a new mainline wiring change. The repeated helper (runner SHA256 prefix 9d5c6050ef2c, GPIO module 70fa6056d80e, lease module 742ea879b244) passed twenty host fixtures before activation. A twenty-second lead-in preceded five ten-second high/low/high/low/high phases, with all ninety-seven samples matching the requested C2 level and C3's sampled pin fields unchanged. Only C2 was requested through normal GPIOv2; C3 was never requested, and no raw-register write was used. The helper restored C2 high while owned, released the GPIO request, then rebound the original I2C1 driver and verified both pin configurations, hidden GPIO state, adapter identity, clocks and PMIC binding. Independent recovery verified the already-restored state, and cleanup removed the temporary RAM files after all diagnostic units became inactive. The menu process and sampled audio state remained in place after the test, with no new kernel log lines. The user thought the rings looked brighter during the repeat, but this uncertain observation does not establish on/off or color control. These results establish the bounded GPIO/driver restoration path; neither a ring mapping nor an audio-noise repair is established.


A current source and original-utility audit found no validated ring-color command. [console-detect at c6b85929](https://github.com/lcdyk0517/console-detect/blob/c6b85929af1971d89174867c6815bb6601e0e971/console_detect.c#L109) still selects unsupported joystick lighting for R36S Plus, and the [current board DTS](https://github.com/lcdyk0517/arkos.bsp.4.4/blob/923a6105701d03fbaa597273a42a49f6434cc4da/arch/arm64/boot/dts/rockchip/rk3326-r36splus-linux.dts) adds no ring controller. The original named color scripts act on GPIO77, already identified as the center light. Passive live inventory exposes only the legacy heartbeat and Wi-Fi LED classes, RK817 as the sole registered I2C client, no SPI client and no saved frontend lighting setting. These scoped negative results do not prove that hardware color control is impossible; a controller interface, protocol or traced channel mapping is still missing. GPIO0_C2 high/low readback and an uncertain brightness impression do not supply an RGB command, so no guessed color sequence was transmitted.

# Channel isolation and standalone audio test, 2026-11-17

The user asked whether the single speaker receives mono audio and requested channel isolation, then a standalone console program with EmulationStation fully stopped. Fresh live readback shows stereo S16_LE at 44,100 Hz with both HP DACs active. Codec register `0x38=0x20` selects L/R mode with its digital mixer disabled. The physical external amplifier's input network remains untraced, so the number of speakers does not establish where or how the two channels combine.

The board's custom Playback control reads the left DAC attenuation and writes the same value to both DACs. Giving that control unequal left/right values would therefore not be a valid channel-isolation test. The reference instead supplies zero samples to the unselected channel and preserves the hardware gain and HP route.

## Incomplete first reference

After normal game exit, a continuous 54-source-second stereo WAV ran while frontend media was suspended. It contained left-only, right-only, identical-both and opposite-both sections. All generated phase samples were independently checked. Runtime PCM ownership and the sampled gain/route remained as expected, but PCM progress was slower than the nominal source rate and playback hit its original 65-second bound, cutting the final section short. The original menu and audio registers were verified restored. This is a retained failed/incomplete comparison, not completed channel or audio acceptance.

The user heard beeps, a pause and another group of beeps, with static/cracks still audible. That description does not identify which of the four phases was heard and cannot establish that both channels combine correctly. A shorter reference with lower monitoring overhead was prepared separately but not activated after the user requested the standalone console application. The first observer's CPU cost was not captured on its error path; its repeated register reads are a confound, and the slower reported PCM progress is not labeled a measured physical sample rate or proof of DMA corruption.

## Standalone hardware results

The following runtime comparisons supersede the preparation-only checkpoint above. The first two-period attempt was stopped by the launcher's startup-geometry assertion and restored the frontend/gain. Its original error path did not preserve unread child output. The second attempt keeps the same ELF and audio configuration, adds actual parameter and child-tail logging, and retains every geometry/error gate. It verifies 44,100 Hz stereo S16_LE, 1,024/2,048-frame period/buffer, an inactive frontend service, no frontend/game processes and application maps containing only its executable, ALSA, libc, libm and the loader. The application then returns EPIPE from snd_pcm_writei after 0.245125 seconds and 7,184 written frames, with no automatic XRUN recovery. This is a captured playback failure, not a successful reference run. It does not alone distinguish userspace scheduling, driver accounting or another device-path problem.

The user reports that the verified frontend-off/PCM-closed interval became quieter. A native ALSA file/null-sink fixture subsequently exercises the complete write/drain loop and produces the exact checked raw reference under UBSan; its only source adaptation disables host tty output. That is userspace fixture evidence, not physical hardware acceptance.

A separately built four-period variant changes only BUFFER to 4,096 frames and reports that profile in its selftest. The period, samples, rate, access method, gain and error gates remain fixed. Both runtime buffer geometries activate the same optional continuous-DMA path, as confirmed by their kernel messages. With the frontend again fully stopped, the larger-buffer application logs all six source phases and queues all 2,293,200 frames. The user reports “Noise still present, similar level” during this verified standalone-stream interval. Thus frontend mixing or a running PSP emulator is not required to reproduce that reported noise; the observation does not identify the responsible analog/digital stage.

The larger run still fails completion: snd_pcm_drain does not complete before the unchanged 105-second application deadline. The application records 0.791948 seconds of CPU time and no XRUN recovery. Across 74 RUNNING samples, application-written frames minus reported delay progress at approximately 29,706 frames per raw monotonic second against configured 44,100. These values depend on ALSA/driver accounting and are not a measured physical DAC clock or proof of sample corruption. Both failure artifacts are retained and classified as failed end-to-end runs; neither error nor completion assertion was removed. The original HP registers/gain and active menu were verified restored after each attempt.

## Standard DMA control and diagnostic corrections

The user power-cycled successfully into boot ID `4ec90cf6-1cc4-4602-91cd-b01027b022bb`. Fresh kernel notes identify the same Image Build ID `ae0578bd8ad04be4b759c32920472861277b2537`; the PL330 parameter is N, and the codec guard remains Y. The original two-period ELF again returns EPIPE: 7,176 frames after 0.243864 seconds. This establishes that enabling the optional continuous feature is not required for that test failure, but the following app-level controls weaken its interpretation as a driver defect.

Instrumented four-source-second digital-zero comparisons retain 44,100 Hz, stereo S16_LE, 1,024/2,048-frame period/buffer, the same kernel and HP gain/route. With the original eager partial-write loop and a 100 ms ALSA wait, EPIPE follows 11,280 frames in 0.352607 seconds; 0.340629 seconds were inside waits, with a maximum of 64.725 ms and no wait timeouts. A temporary `/dev/cpu_dma_latency` request of zero does not prevent EPIPE (7,176 frames in 0.231186 seconds). Its descriptor closes in the guard's finally path, and the effective request is verified back at the original 2,000,000,000 value. No CPU policy or latency request remains installed.

Reducing the wait timeout to 5 ms lets the eager writer queue every source frame, but exposes an error in the diagnostic's drain-completion test. Additional live logging verifies that the stream reaches SETUP with zero delay while repeated nonblocking drain calls continue returning EAGAIN. The retained ALSA 1.2.14 hardware backend bypasses the common state check and directly issues DRAIN; the kernel's nonblocking ioctl returns EAGAIN even after drain initialization encounters SETUP. The corrected program explicitly queries `snd_pcm_state()` after drain, requires SETUP for completion, and still rejects unexpected states, errors and deadlines. See the primary [ALSA hardware backend](https://github.com/alsa-project/alsa-lib/blob/v1.2.14/src/pcm/pcm_hw.c) and [common PCM implementation](https://github.com/alsa-project/alsa-lib/blob/v1.2.14/src/pcm/pcm.c). Previous deadline artifacts remain failed test executions, but they do not prove the hardware was still draining; no drain-state sample was retained for the earlier full-length run.

With that correction, the short 5 ms profile writes all 176,400 zero frames, reaches SETUP, closes PCM and restores the menu/gain, returning zero in 5.807468 seconds without XRUN recovery. A separate eager-write comparison with ALSA period events enabled and the original 100 ms timeout also completes (5.860288 seconds, 171 waits, no timeouts). A final comparison synchronizes availability and waits until an entire requested period fits before writing, leaving period events disabled and retaining the 100 ms timeout. It completes in 5.848280 seconds with 171 waits, zero timeouts and zero partial writes. All failure checks remain active. The current diagnostic defaults to this period-aligned writer; `WHOLE_PERIOD_WRITES=0` retains the earlier eager stress profile. These comparisons show that writer alignment and notification strategy affect this small-buffer reproduction; they do not establish a production driver fix or clean sample contents.

Only digital silence was used in those short profiles. Four seconds of source takes approximately 5.85 seconds of raw elapsed time in the latter comparisons, including startup and drain. This discrepancy is unresolved and is not a measured DAC sample rate. An independent five-second PC/handheld clock handshake bounds their raw elapsed-time ratio to approximately 0.981–1.010, excluding a one-third global timescale mismatch for that interval. Read-only CRU/PLL and I2S decoding still specifies 11.2896 MHz divided by 4 and 64, implying configured 44,100 Hz; programmed dividers do not measure the physical output clock. No clock register was changed. DMA IRQ counters and parameter readbacks are preserved with the captures, but are not promoted to sample-integrity evidence.

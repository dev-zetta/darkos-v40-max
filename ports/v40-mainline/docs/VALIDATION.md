# Mainline migration status, 2026-11-15

See the [image r2 emulator results](../EMULATORS.md) for the later development-card display, control, and Super Mario 64 replay checks. Those measurements use the installed development builds and a populated Mesa cache.

The [7.3.4-v40.1 kernel update](../KERNEL_RELEASE.md) uses the probe-time I²S1 correction. On the same build the user verified a normal cold boot and heard the tested PPSSPP game play without its former scrambling. The [live playback check](AUDIO_CONSOLE_20261117.md) recorded the corrected 600 MHz input, approximately 44,101 frames per second and zero ALSA XRUNs. The release uses standard PL330 DMA. In a separate USB comparison, an extension that moved the Wi-Fi dongle away stopped repeating speaker cracks. USB link mode remained at 480 Mb/s and Wi-Fi remained usable. Steady speaker static and the menu-entry pop remain open.

The [standalone console audio diagnostic](AUDIO_CONSOLE_20261117.md) has strict native/ARM64 builds, independent full-stream channel checks and exact ARM64/native generated-PCM agreement. With the frontend fully stopped, a two-period run returned EPIPE and a four-period run queued the full source but timed out during drain. The user reports similar noise during the standalone stream and less noise with PCM closed. The same-Image standard-DMA control has now booted. After correcting the diagnostic drain check and aligning period writes, short digital-zero runs completed without XRUNs. A full reference completed transfer, drain and restoration on 2026-11-18. The user heard no beeps on the repeat. Follow-up measurements found that the I2S frame clock runs slowly during standalone playback despite the nominal divider settings. The user later heard three left-only beeps. Two controlled comparisons traced the timing slowdown to a 1.2 GHz input on the PX30 I2S1 fractional divider, which specifies a 600 MHz maximum, and reproduced its dependence on the GPU and logic-rail operating point. The temporary compliant configuration corrected transfer timing. The earlier media-paused reference hit its playback bound and is retained as an incomplete comparison.

The [2026-11-17 routing audit](AUDIO_ROUTING_20261117.md) confirms that the installed DTB matches the retained compiled artifact and that its audio, PMIC, I2S and pin properties match the running tree. Issue519's vendor amplifier boolean does not apply to the current mainline driver. The inherited output graph remains incomplete, but current HP hardware state, NORMAL buck modes and factory-matching backlight PWM do not establish a configuration fix for the unresolved pop or noise.

The original installation now runs Linux 7.3.4-v40.1 with private Mesa/Panfrost and SDL. The user confirmed a working menu, normal display and controls, speaker music after clean shutdown/power-on, Wi-Fi/SSH, and the latest PSP rendering and FN/SELECT/START correction. Existing games, saves and user settings were preserved during the installation migration. These observations apply to the tested RK3326 720x720 wiring, not all products sold as V40/R36S.

The kernel is a port from the signed upstream Linux 7.3.4 release, not the old 4.4 BSP with its version string changed. The board device tree, ST7703 command/power sequence, gamepad APIs and board-scoped RK817 mixer compatibility are carried as source. Native rtw89_8851bu replaces the legacy out-of-tree AX900 Wi-Fi driver. The working speaker path uses the headphone DAC (Playback Mux HP) on this board; the silent SPK route must not be restored based solely on the absence of a headphone jack.

PSP displayed its FPS overlay over a black game image while SkipBufferEffects was enabled. Disabling that setting restored the tested game image. SDL 2.32.10 selected an incomplete CRC-specific automatic controller mapping instead of the retained generic entry, omitting SELECT, START and guide/FN. A complete entry for GUID 1900bb3e4b4800000011000000010000 restores them; guide becomes PPSSPP key code 4, so Pause also needs 10-4. Three existing per-game profiles overrode the global controls and received the same additive binding. SELECT+START already worked through the separate evdev exit service. The user subsequently reported that all requested rendering/button checks work.

The current deployed diagnostic kernel includes a default-off, board/channel/geometry-scoped PL330 continuous-DMA experiment, enabled explicitly on the test installation. Both the 8 KiB PSP ring and 16 KiB menu ring were observed on that path, but audible scrambling persisted. This is not an accepted audio-quality repair. Host fixtures and module CRC checks establish bounded software/ABI evidence only. Retain the original PL330 path as the default when publishing the source recipe.

Intermittent audio defects remain unresolved, with two distinct observations in the later follow-up. Alien Syndrome ran at roughly 58–68 percent emulation speed with a depleted PPSSPP resampler queue and rising emulator underruns; changing global rendering from Auto to 1x PSP brought the tested scene near 100 percent and made its music cleaner according to the user. Both launcher configuration copies retained 1x after normal exit. Independently, the user hears idle static/cracks with menu music disabled: five exact-zero PCM-ring snapshots and a minimum-DAC-level comparison did not account for that noise, while closing playback made it much quieter and stopped the cracks. This implicates the active output path without establishing a specific codec, amplifier or power defect. See [the dated investigation](AUDIO_INVESTIGATION_20261115.md). Early USB PHY clock-cleanup warnings, software-reboot display repeatability, headphone transitions, suspend/wake, sustained thermal behavior and broader emulator coverage remain follow-up work. Clean shutdown followed by power-on is the established working boot path.

The AudioManager callback notification fix was activated as frontend V4 with both integrity consumers updated, without an accepted audible improvement. The current V6 frontend retains that change and adds native battery discovery/voltage, status geometry and START-menu footer fixes; the public twelve-patch series reproduces it. A live framebuffer shows percentage and charging bolt beside Wi-Fi/Bluetooth. The experimental perfmax governor change was activated and then rolled back after two PSP-launch freezes; the old helper restored successful launch. The tested userspace policy/transition path remains suspect, while 480 MHz itself is not established as the cause because the old simple_ondemand path also reaches it successfully. The separate post-PHY-rearm candidate remains excluded from the default kernel patch set.

The battery follow-up identified missing external-DC input support and retained mainline gauge defects. The new 7.3.4-v40.1 build passed exact configuration/export/module ABI checks and a user cold boot; live identity matches build 9b073e539870f55bc27441bee8e625b03fafc5ee. With the adapter connected it now reports Charging and ONLINE=1, where the prior build reported Not charging and ONLINE=0 despite positive current. Boot retained the counter's approximately 67 percent instead of deriving a full-charge estimate from charger-biased PWRON voltage. The user confirmed charging-icon transitions and the START-menu BAT percentage. The user's twenty-point same-boot jump was not reproduced, a full charge/discharge calibration is unverified, and no audio repair is established. See [the dated battery/status report](BATTERY_STATUS_20261116.md).

Runtime configure-ppsspp.py is the reusable settings equivalent of the installed PSP correction. It defaults to a plan, requires an explicit new backup directory for writes, preserves existing pause alternatives and unrelated settings, and refuses to modify settings while a PPSSPP process is detected. Confirm the exact board identity and exit the game before using it. The helper does not claim hardware discovery, whole-image rollback, or power-loss atomicity across several files.

The subsequent [controlled idle-noise comparisons](AUDIO_ANALOG_20261116.md) verified current-kernel digital zeros, DACMT-only muting, normal-DAPM codec output shutdown and restoration, and menu-thread pause/resume with continuing PCM. The user reported unchanged noise during mute/output shutdown and more cracks during thread pause. Removing the USB adapter stopped repeating cracks while static remained, with cracks returning after reconnection. A standard WLAN power-save-off comparison did not help and was restored. These observations narrow the investigation without establishing an analog hardware defect, a missing codec patch or a permanent mitigation.

A completed WLAN-only soft-block comparison did not suppress the noise while the composite dongle remained attached. These different boot/power/hub conditions do not identify one defective component.
